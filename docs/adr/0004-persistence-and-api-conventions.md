# Persistence: app-generated ids, no database in tests, invariants in the application only

**Identity.** `WorkLog` and `Plan` carry a non-null `UUID id` directly in the domain record. The application generates it (UUIDv4 via `UUID.randomUUID()`), not the database, so a new object is complete before it is saved. New objects are made with a static factory (`WorkLog.create(...)`, `Plan.create(...)`); the canonical constructor with an id is reserved for entity mappers and tests. We chose a factory over a second constructor without an id, because two similar constructors make it easy for a mapper to call the wrong one and silently mint a new id. Value types (`BudgetItem`, `HourlyRate`, `Money`) have no id. The owning user stays out of the domain: it is a `user_id uuid` column filled from the JWT subject.

**Testing without a database.** Controllers are tested with mocked services, and services and entity mappers with unit tests. There is no Testcontainers and no H2. The schema is checked only when the application starts against Supabase with `ddl-auto: validate`. We accept that repository queries and Liquibase migrations are not covered by automated tests, in exchange for no new dependencies and fast tests. Revisit if a query bug slips through.

**Invariants only in the application.** Domain rules (non-overlapping Earning Windows of one user, minutes per Work Log, positive amounts) are enforced in domain records and application services. The database has `NOT NULL`, primary and foreign keys, but no exclusion constraint (`btree_gist` on `daterange`) and no `CHECK` constraints. Only Spring writes to the database (ADR 0001), so a rule lives in one place and changing it needs no migration. The cost is that two concurrent requests could create overlapping plans, and manual edits in the Supabase SQL editor are not guarded. Add the exclusion constraint and simple `CHECK`s before the beta.
